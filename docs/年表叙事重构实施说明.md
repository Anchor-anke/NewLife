# 年表式叙事重构 · 实施说明

> 对应方案：`docs/年表叙事重构方案.md`
> 本文记录**实际做了什么、为什么这么做、哪些地方没有照方案写、验证到了什么程度**。

---

## 一、重构的目标范围

把叙事单位从「回合」换成「段落 + 条目」，让游戏从「读小说 + 每步选一次」变成
「读年表 + 只在岔路口停车」。

涉及四层，按依赖顺序自下而上：

| 层 | 模块 | 变化 |
| --- | --- | --- |
| 数据契约 | `engine/types.ts` | 新增 `LifeEntry` / `LifeSegment` / `SegmentProposal` / `DecisionPoint` / `LifeSegmentRecord` / `PendingSegment`；`SCHEMA_VERSION` 1→2 |
| 节奏参数 | `engine/pacing.ts` **（新增）** | `timeAdvanceHint` / `expectedSegments` / `decisionIntervalFor` + 决策密度常量 |
| 决策判定 | `engine/decision.ts` **（新增）** | `planStop`（调用前）/ `resolveDecision`（调用后门槛） |
| 结构校验 | `engine/schema.ts` | `segmentProposalSchema`（含「流水账」校验）；旧回合结构保留为迁移专用 |
| 数值规整 | `engine/normalize.ts` | `normalizeSegment`：条目清洗 + **年龄校正** |
| 规则结算 | `engine/resolve.ts` | `resolveSegment`：**条目级推进**、**一段内多次突破**、寿元截断 |
| 提示词 | `engine/context.ts` | 条目流输出契约、「本段必须停车」强制指令、近期历史只喂条目 |
| 管线 | `engine/segment.ts` **（替代 `turn.ts`）** | `runSegment`：算停车 → 组装 → 调用 → 校验（含「必须有决策点」）→ 规整 → 结算 |
| 记忆 / 摘要 / 辅助 | `engine/memory.ts`、`summary.ts`、`suggest.ts` | 跟随段落化；`suggestOption` 改为接 `DecisionPoint` |
| 数值模拟 | `engine/simulate.ts` | 段推进 + **决策次数统计** + 新不变量 |
| 存储 | `storage/db.ts`、`saves.ts`、`migrate.ts` | Dexie v3 表改名搬迁；v1→v2 纯函数升级链；v1 导出包兼容 |
| 服务 | `services/segmentService.ts` **（替代 `turnService.ts`）**、`gameService.ts` | 提交单位改为段落 |
| 界面 | `app/play/PlayClient.tsx`、`components/game/{Timeline,DecisionCard,AdvanceBar}.tsx` | 年表视图 + 事件流视图 + 决策卡 + 推进控制 |
| 脚本 | `scripts/mock-model-server.mjs`、`scripts/e2e-check.mjs` | 条目流契约、按段数等待、决策卡场景 |

删除：`engine/turn.ts`、`engine/turn.test.ts`、`services/turnService.ts`、
`components/game/ActionPanel.tsx`。

## 二、要解决的主要问题

### 1. 职责边界被「回合」这个单位压扁了

重构前，`resolveTurn` 同时承担四件事：应用属性变化、结算修为、判定突破、判定死亡。
「一段跨越多年」之后这些事必须在**时间轴上**发生，而不是在一段的首尾各发生一次——
否则「闭关三十年，第三年就寿元耗尽了」这种矛盾会直接写进叙事里。

现在 `resolveSegment` 沿条目推进，每一小步都结算积累、突破与死亡，寿元耗尽时
**截断到那一条**，`timeAdvance` 记为实际推进的年数。

### 2. 决策频率没有任何程序侧的约束

原设计把「下一步做什么」完全交给模型，模型给几个选项玩家就做几次决策。
一局 70 次决策，边际意义递减到零。

现在决策密度由 `pacing.decisionIntervalFor(world)` 按世界的段落规模反推，
外加「任意 2 段内最多 1 次」的硬上限，并有数值模拟的断言守着。

### 3. 「回合」词汇渗进了每一层

`latestTurnId` / `summarizedThroughTurnId` / `totalTurns` / `atTurnId` /
`pendingTurns` / `GameTurnEvent` / `TurnStage` / `runTurn` / `submitTurn`……

这次统一换成段语义（`latestSegmentId` / `atSegmentId` / `PendingSegment` / …）。
**留在代码里的旧词汇会持续误导下一个读代码的人**，改名本身就是可维护性的一部分。

### 4. 长文本 + 高频决策的组合在提示词里没有任何约束

现在提示词明确区分「条目」与「detail」，并给出「什么算重要」的清单；
程序侧还有一条硬约束：连续 3 条同类型的条目判为流水账，回灌重试。

## 三、重构遵循的约束

1. **架构铁律不变**
   - 模型只提议，程序才结算（决策点同样如此）
   - IndexedDB 是唯一状态真源，不引入第二份内存状态
   - 进度类属性（修为）是程序拥有的量，模型给出的增减一律忽略并记警告
   - 三层记忆的窗口与摘要必须无缝拼接（`verifyMemoryCoverage` 守门）
   - `schema.ts` 只判形状（失败→回灌重试），`normalize.ts` 只修数值（从不抛错）
   - 引擎与界面保持题材无关（`worlds.test.ts` 的源码扫描守卫未动）
2. **外部接口不变**：OpenAI 兼容适配层、导出/导入、自定义世界生成管线全部保持原样。
3. **不重写世界观的数值设计**：四个内置世界的寿元表、积累曲线、突破难度一个数字都没改。
   只有两个字段改了名（见下）。
4. **旧存档必须还能打开**：`schemaVersion` 升到 2，v1 存档与 v1 导出文件都能升级。
5. **每一处行为变化都有测试兜底**：新增 `decision.test.ts`，重写 `engine.test.ts`，
   数值模拟新增两条不变量。

## 四、与方案的偏差（重要）

方案里有几处内部不自洽的地方，实施时按「哪个更接近方案自己的目标」做了取舍。
以下逐条列出，便于复核。

### 1. 单段跨度上限：25 年 → **60 年**

方案同时要求「一段 3~25 年」和「一局 30~60 段」。但青冥仙途的终局寿元是 3400 岁：
按 25 年封顶，一局必然碎成 **130 多段**，与它自己的段数目标直接冲突。

实施取法：真正的锚点是「**终局寿元 ÷ 目标段数**」（`pacing.TARGET_SEGMENTS_PER_LIFE = 60`），
`TIME_ADVANCE_MIN/MAX = 3/60` 只是防止模型给出离谱值的兜底。这样短寿元的世界一段几年、
长寿元的世界一段几十年，玩家体感一致。

### 2. 每局段数：30~60 → **实测 27~78**

| 世界 | 终局寿元 | 实测平均段数 |
| --- | --- | --- |
| 浮生记 | 105 岁 | 26.8 |
| 星海孤舟 | 720 岁 | 64.7 |
| 灰烬王座 | 560 岁 | 66.7 |
| 青冥仙途 | 3400 岁 | 77.7 |

两端各自贴着上下限：现代世界受「单段至少 3 年」约束凑不满 30 段，
修仙世界受「单段至多 60 年」约束压不到 60 段以下。

因此断言写成**按世界尺度缩放的下限**（`simulate.requiredMinSegments`）加上限 90——
这与既有的 `requiredDistinctTiers` 是同一种处理，表达的是
「这个世界有没有发挥出它自己的潜力」，而不是拿一把尺子量所有题材。

### 3. 决策密度：目标 8~15 **已达成**，但门槛不是固定常量

四个世界的实测平均介入次数：**8.2 ~ 13.9**（三种模型形态下全部落在方案的目标区间内，
   见第五节的三张实测表）。

但方案给的是固定阈值（「≥8 段」「≥3 段」）。实测固定常量做不到：段落数跨度
27~78（2.9 倍）时，同一个常量要么让短局几乎没有介入，要么让长局决策泛滥。

改为 `pacing.decisionIntervalFor(world) = clamp(估算段数 ÷ 10, 3, 12)`，
按世界的规模反推。这与方案的分工原则一致——**节奏参数属于程序负责的部分**。

### 4. 「连续 3 段没有任何决策」这条兜底条件的落点

方案把它和「距上次决策 ≥8 段」并列为**调用前的 mustStop 条件**，但两者语义重复
（都是「距上次决策的段数」），后者完全覆盖前者。

实施为**调用后的兜底门槛**：距上次介入达到 `decisionInterval` 之后，模型主动提的岔路一律放行。
这样三条条件各司其职，没有一条是冗余的：

| 条件 | 作用点 | 职责 |
| --- | --- | --- |
| 距上次介入 ≥ 决策间隔 | 调用前 `planStop` | 在提示词里下强制指令，逼模型产出素材 |
| 寿元进入末 15% | 调用前 `planStop` | 同上，且让「收束这一生」的岔路有机会出现 |
| 距上次介入 ≥ 决策间隔 | 调用后门槛 | 放行模型主动提的岔路（主要密度来源） |
| 本段发生突破 / 幅度达标 / 命中关键词 | 调用后门槛 | 真正「重大」的段落随时可以停 |

前两行与第三行**用的是同一个数**（`decisionIntervalFor`）——程序在这个间隔上
要一次岔路，模型给了就采纳，正好构成一次介入。

### 5. 条目默认展开规则

方案正文写「`milestone` 或**带 detail** 的条目默认展开」，但它自己的界面草图里，
带 detail 的挫折条目是折叠的（显示「⌄ 展开」），只有 milestone 是展开的。
而且按正文实现会让「一屏能看到 20~40 年」的目标落空——模型多给几个 detail 就回到原样。

实施按草图：**只有 `kind === 'milestone'` 默认展开**，其余点击才展开。

### 6. 两个字段改名

`maxDeltaPerTurn` → `maxDeltaPerSegment`，`turnSoftLimit` → `segmentSoftLimit`。
语义随叙事单位变化了，名字不改就是主动留一个坑。四个内置世界与 `forge.ts` 一并更新，
**数值一个没动**。

### 7. 新增 `LifeSegment.legacy` 标记

方案要求「旧存档迁移后界面按旧版长文样式渲染」，但没说界面怎么知道哪一段是迁移来的。
实施给迁移产生的段落打 `legacy: true`，界面显示「旧版记录」徽标。

### 8. 条目长度：≤25 字 → **15~40 字**

这一条不是实施时定的，是**上线后收到产品反馈才改的**：条目「周砚捎信，得一子，唤作念山」
读起来像电报。根因是提示词的三处措辞都在往省字的方向推，详见第五节
「条目文案的 register」。

## 五、关键实现说明

### 条目是权威时间轴

`normalize.cleanEntries` 把模型给的 `age` 压成「单调不减且落在 `[当前年龄, 段尾]`」；
`resolveSegment` 沿条目逐条推进，每条都结算积累 → 突破 → 死亡。

```
段起 16 岁，timeAdvance 10，条目年龄 [18, 20, 24, 26]
  → advanceTo(18) 结算 2 年 → 突破判定 → 死亡判定
  → advanceTo(20) 结算 2 年 → …
  → advanceTo(24) 结算 4 年 → 若这里寿元耗尽，后面的条目整段丢弃
```

### 一段内的多次突破

跨度变长之后，一段里连续突破两三次是正常的。`runBreakthroughs` 循环处理，
上限 `MAX_BREAKTHROUGHS_PER_SEGMENT = 5`，达到上限时剩余进度结转到下一段并记警告。

**计数器放在段落作用域而不是循环内部**——一次段落推进会被条目切成好几小步，
每小步都跑一次突破判定；上限若按小步计数就等于没有上限。

### 决策门槛

```
调用前 planStop(world, character, segmentId, lastDecisionSegmentId)
  ├─ 距上次介入 ≥ 12 段        → 提示词里写「本段必须给出一个决策点」
  └─ 寿元进入当前阶位末 15%    → 同上

调用后 resolveDecision(...)
  ├─ 距上次决策 < 2 段         → 无条件丢弃（硬密度上限优先于一切门槛）
  ├─ 本段发生突破              → 采纳，成因 breakthrough
  ├─ planStop 命中             → 采纳，成因 long-gap / near-end
  ├─ 属性总变动 ≥ 25           → 采纳，成因 proposed
  ├─ 条目命中分量关键词        → 采纳，成因 proposed
  ├─ 距上次介入 ≥ 决策间隔     → 采纳，成因 proposed（兜底）
  └─ 都不满足                  → 丢弃，记警告，不打断玩家
```

`deltaMagnitude` 刻意**排除进度类属性**：修为由程序结算、量级天然很大，
算进去的话几乎每一段都会通过门槛。

### 决策密度的状态只有两个数字

`SaveRecord.latestSegmentId` 与 `SaveRecord.lastDecisionSegmentId`。
`lastDecisionSegmentId` 由 `commitSegment` 从段落本身推导（带决策点的段落就是最后一次停车），
不额外传一份——同一个事实只有一个来源，也就不会对不上。

好处是多标签页、崩溃恢复、导出导入都不需要额外处理决策状态。

### 实施过程中被测试抓到的两个缺陷

写在这里是因为它们都属于「不跑起来根本看不出来」的那一类：

1. **突破次数上限的计数器放错了作用域。** 一开始写在 `runBreakthroughs` 的循环内部，
   而一次段落推进会被条目切成好几小步、每一小步都调一次它——上限等于没有，
   一段内突破 6 次。计数器必须放在**段落作用域**。
2. **`integer: true` 的属性没有在最后取整。** 程序结算的修为是
   「每年积累量 × 年数」逐条目累加出来的浮点数，误差一路带到界面上，
   状态面板显示成「修为 87.60000000000001 / 100」。
   取整统一收到 `clampAttribute` 里，一处生效。

另外，端到端的模拟服务曾经**按提示词措辞分派请求**，提示词改说法之后分派静默落到
「段落生成」分支，表现为「AI 建议出不来」。现在改为按输出契约
（`"index"` / `"action"` / `"entries"`）分派，认不出时在控制台出声。

### 模型不给决策点时怎么办（方案没写的一种失败）

方案的风险表只覆盖了「模型**到处**提议岔路」，没写反过来的情况。而反过来的后果更严重：

- 原来（只记警告放行）：一个总是不给岔路的模型会让玩家**整局一次都出不了手**，
  游戏退化成看小说——正是这次重构要解决的问题。
- 只加重试、失败就报错：模型三次都不给，整局在第一个强制停车点**直接卡死**，
  比没有岔路更糟。

最后的处理是两者之间：

1. 程序判定必须停车时，把「必须有决策点」当成**本次调用的输出契约**，
   `parseSegmentProposal(raw, { requireDecision: true })` 会判它结构不合格，
   走已有的回灌重试通道（错误信息点名 `decision`，模型知道该补什么）。
   这一层做这件事而不是让结算层兜底，是因为**程序替模型编一个「继续 / 停下」式的
   通用岔路，等于给玩家一个假的选择**。
2. **最后一次尝试放宽这条要求**：三次都不给就照常结算并记一条警告，
   而不是把整局卡死。
3. 缺失是**自愈且有界**的：`lastDecisionSegmentId` 没有推进，
   下一段的 `planStop` 依然判定必须停车，提示词会继续要求。

覆盖它的测试在 `segment.test.ts`：漏了 → 重试一次补上；三次都不给 → 带警告结算；
程序没要求时 → 不给也直接通过；模型主动给了但没到门槛 → 走门槛判定而不是浪费重试。

### 条目文案的 register：短，但不等于压缩

第一版上线后收到一条产品反馈：条目「周砚捎信，得一子，唤作念山」太简短了。

诊断下来，问题不在长度本身，而在**提示词给错了示范**：

- JSON 示例里放的是占位符（`"text": "一句话，25 字以内"`），模型拿不到任何 register 参照；
- 规则写着「**一句话**，25 字以内，要能被一眼扫过」，正文又说「其余一律是一句话」——
  三处都在往「省字」的方向推。

模型于是学会了把一件事提炼成主谓宾摘要。改法是四件事：

1. **示例换成真实条目**，并刻意做成对照：把「电报体」和「有质地的一行」并排放。
   对模型来说，一个反面例子比三行规则管用。
2. 长度 25 字 → **15~40 字，一到两句话**。
3. 明确禁止摘要式写法：「与师父决裂」是摘要，「你把师父留下的剑放在山门口，没有回头」
   才是发生过的事。**省掉的是细节，不是句子本身。**
4. 规整层的截断上限 40 → **60 字**。截断本身有代价——一句写到一半被切断比短句更难看。

这条改动的边界要说清楚：它**没有**推翻「默认短，重要才长」。条目仍然是一行、
仍然可扫读，一屏仍然能看到几十年。变的只是每一行的质地。
按 4~12 条、每条 15~40 字估算，一段约 200~400 字，一局 45~78 段合计 1~3 万字——
仍远低于重构前那个「每回合读 300~800 字」的量级。

### 决策门槛按信号强度分层（一次实测抓到的校准错误）

模拟器里条目文案是中性的（`模拟条目 N`），**从不命中**「分量关键词」这道门槛。
于是模拟报出「每局 9.1 次介入」，看着完美——但真实模型写出来的条目几乎必然会命中。

把文案换成带分量词的版本重测，数字是这样的：

| 世界 | 段落 | 介入（中性文案） | 介入（带分量词） |
| --- | --- | --- | --- |
| 青冥仙途 | 77.7 | 9.1 | **38.6** |
| 灰烬王座 | 66.7 | 8.4 | **33.1** |
| 星海孤舟 | 64.7 | 8.1 | **32.1** |
| 浮生记 | 26.8 | 8.7 | 12.9 |

一局停车三十多次，比原来的回合制还累。根因是**门槛按「能不能命中」判断，
却没按信号强度分层**：关键词只是一个词，却能贴着硬密度下限（2 段）把玩家叫回来。

修法是给弱信号单独设一道间隔门槛（`KEYWORD_MIN_GAP = 6`），
而强信号不受限制——阶位突破、程序侧强制、属性总变动达标都是程序结算出来的**事实**，
不是措辞。收紧后：13.9 / 12.0 / 11.5 / 8.7，两个极值都落进 8~15。

`balance.test.ts` 现在**两种文案风格都跑**，这是永久回归守卫：
只测下限会给出虚假的安全感。

顺带修掉一个度量口径问题：`minDecisionGap` 原来把「第一次停车」算成 `gap = segmentId`，
于是「第一段就停车」会被误报成「违反了 2 段下限」。硬密度上限本来对第一次停车是豁免的
（它防的是「连着停两次」），度量口径应当一致。

### 介入次数的下界同样要按世界规模反推

模拟器一直只跑「模型每段都提岔路」这一种形态——那是**上界**。补上
「模型只在被强制时才提」（一个遵守指令但从不主动的模型）之后：

| 世界 | 段落 | 话多 · 中性 | 话多 · 带分量词 | **只被强制时才提** |
| --- | --- | --- | --- | --- |
| 青冥仙途 | 77.7 | 9.1 | 13.9 | **6.6** |
| 浮生记 | 26.8 | 8.7 | 8.7 | **2.0** |
| 灰烬王座 | 66.7 | 8.4 | 12.0 | **5.8** |
| 星海孤舟 | 64.7 | 8.1 | 11.5 | **5.8** |

浮生记只有 **2.0 次**——玩家整局几乎出不了手。根因和上一次同源：**绝对常量**。
`MUST_STOP_GAP = 12` 对平均 26.8 段的世界等于「一局最多停两次」。

修法是让这条间隔也按世界规模反推：`decisionIntervalFor(world)`。
**一个数服务两件事**，而不是两个：

| 作用点 | 效果 |
| --- | --- |
| 调用**前**（`planStop`） | 达到它就在提示词里下「本段必须给出一个 decision」，把吝啬的模型叫回来——这是介入次数的**下界** |
| 调用**后**（`resolveDecision`） | 达到它，模型主动提的岔路就放行——这是**上界** |

同一个数能同时管两侧，是因为两条路径不冲突：程序要一次岔路，模型给了就采纳，
正好构成一次介入。

#### 中间走过一段弯路，值得记下来

我一度把它拆成**两个**间隔（一个管上界、一个管下界），理由是「两侧需求相反：
`compliant` 模式下突破不占介入预算，`eager` 模式下每次都占」。这个论证听起来
很顺，但它是从一个**不可靠的算术模型**推出来的，不是实测。

后来把那句话本身当成待验证的假设，做了个实验——把两个间隔合并成同一个数再跑一遍：

| 世界 | 实际段数 | 合并后间隔 | 话多 · 中性 | 话多 · 带分量词 | 只被强制时才提 |
| --- | --- | --- | --- | --- | --- |
| 青冥仙途 | 77.7 | 9 | 10.5 | 13.9 | 8.6 |
| 浮生记 | 26.8 | 3 | 8.7 | 8.7 | 8.2 |
| 灰烬王座 | 66.7 | 7 | 10.8 | 12.0 | 9.2 |
| 星海孤舟 | 64.7 | 7 | 10.4 | 11.5 | 9.0 |

三种形态全部达标——**论证被实测证伪**。于是删掉多余的那个旋钮：
少一个参数，就少一处会漂的地方。

教训：**「听起来合理」的架构论证必须当成待验证的假设。** 这类论证的成本不在于
写错了，而在于它会以注释和文档的形式固化下来，让后来的人不敢动。

### 但真正的病根是估算公式，不是除数

改完除数之后，四个内置世界都进区间了，**`forge.test.ts` 却开始失败**：
AI 生成的世界冲到 18.9 次。查下去发现，问题的层次比我以为的深一层——

`expectedSegments` 原本用「**终局寿元**」当参照，等于假设角色一定活到最高阶位。
多数人生会提前结束，所以估算值系统性偏大，而且**偏差幅度不稳定**：

| 世界 | 估算 | 实际 | 偏差 |
| --- | --- | --- | --- |
| 青冥仙途 | 209 | 77.7 | +169% |
| 灰烬王座 | 124 | 66.7 | +86% |
| 星海孤舟 | 120 | 64.7 | +86% |
| 浮生记 | 30 | 26.8 | +12% |
| AI 生成的世界 | 53 | 57 | **−7%** |

**用一个除数去抵消一个不稳定的偏差，必然顾此失彼**：把内置世界调好的除数，
放到偏差方向相反的生成世界上就完全失效。

修法是改参照：取「**中上阶位**」的寿元（`TYPICAL_TIER_RATIO = 0.75`）代表
一个典型人生能达到的高度，而不是拿最高阶位。偏差随即收敛到 +6%~+23%，
剩下的这点余量用一个统一除数就吃掉了。

最终实测（四个内置世界，三种模型形态）：

| 世界 | 估算段数 | 实际段数 | 决策间隔 | 话多 · 中性 | 话多 · 带分量词 | 只被强制时才提 |
| --- | --- | --- | --- | --- | --- | --- |
| 青冥仙途 | 88 | 77.7 | 9 | 10.5 | 13.9 | 8.6 |
| 浮生记 | 33 | 26.8 | 3 | 8.7 | 8.7 | 8.2 |
| 灰烬王座 | 71 | 66.7 | 7 | 10.8 | 12.0 | 9.2 |
| 星海孤舟 | 74 | 64.7 | 7 | 10.4 | 11.5 | 9.0 |

三种形态全部落进 8~15，AI 生成的世界也通过。

**三次都栽在同一件事上：把节奏参数写成绝对常量。** 这是这套系统里最容易复发的
一类错误——新增世界、改段跨度、改寿元表之后，都该先看这张表有没有漂。

### 输出上限：典型更省，但最坏情况更大

重构把一次调用的输出从「300~800 字长散文 + JSON」换成了「4~12 条一句话条目 +
少量 detail」。直觉上这是**更省**的——典型情况确实从约 1200 字降到约 800 字。

但**上限反而变大了**，因为条目有 JSON 结构开销（每条约 60 字符的骨架），
12 条都带 detail、再叠上一个决策点，可以到 5000 token 上下。

所以 `DEFAULT_SETTINGS.maxTokens` 从 4000 提到 **6000**，设置页的提示也重写了。
这个失败形态很隐蔽——「空内容 + `finish_reason: length`」在界面上完全看不出是截断，
而且它只在「模型这次特别爱给详情」时才出现，跑几十次都碰不到一次。
多给的额度不生成就不计费，所以宁可给宽。

### AI 生成世界的校验也补上了两侧

`forge.ts` 的校准循环最后只用**单形态**跑 `checkInvariants`。而密度是唯一依赖
模型形态的不变量——`eager` 是上界、`compliant` 是下界，且 `eager ≥ compliant`
（突破只在有提议时才会占掉一次介入机会）。所以「上界刚好达标、下界不达标」
在结构上是可能的，单形态校验看不见。

改成 `checkInvariantsAcrossForms(world, count)`：常规不变量跑一次（它们与模型形态
**无关**——三种形态的随机数流完全一样，重复跑只会产生三份几乎相同的报告），
密度则上界、下界各跑一次。

**诚实说明：这个守卫今天没有抓到任何东西。** 加进去之后 `forge.test.ts` 全过，
说明现有夹具在三种形态下都达标。它补的是一个结构上看得见的缺口，不是修一个
正在漏的洞。保留它的理由是成本很低（两次额外模拟），而缺口本身是真实的。

顺带记录一个已知的取舍：调参循环里仍然用单形态（每轮都跑，反馈要便宜），
所以如果将来某个生成世界只在某一侧不达标，循环不会去修它——它会作为
「校准后仍未达标的项」如实报给玩家。这比静默放过要好。

### 旧存档迁移

- **表结构**：Dexie v3 把 `events` → `segments`、`pendingTurns` → `pendingSegments`，
  旧表声明为 `null` 表示升级后删除但 upgrade 期间仍可读。
- **对象形状**：`migrate.ts` 里是一条纯函数升级链，导出导入与 Dexie 升级共用同一份实现。
- **回合 → 段落**：`entries` 用 narrative 首句、`detail` 放完整 narrative；
  旧回合末尾的 `options` 转成一个决策点，这样旧存档能从那一步接着玩。
- 已结束的存档会摘掉最后一段的决策点（`stripTrailingDecision`），
  否则界面会在一个已经收束的故事末尾弹出一张无法继续的决策卡。

以下为基线形态（模型话多 + 中性文案）的实测：

### 端到端覆盖

`scripts/e2e-check.mjs` 已按新契约重写（50 项，七个场景），关键几项：

- **年表**：条目按年份分组（实测一屏可见 15 个年份分组）
- **视图切换**：年表 ↔ 事件流，并断言事件流**确实不分年**（年份分组数为 0）
- **推进控制**：`连续推进 ×5` 到终局；中途点「暂停」能真的打断（实测推进 2 段后停下），
  且暂停之后还能继续单步推进
- **结局**：结局面板 → 生平总结 → 存档标记已结束
- **崩溃恢复**：在决策卡上点了选项后立刻刷新 → 提示「上一段未完成」且带上当时的决定
  → 重试补上这一段
- **决策卡**：程序门槛采纳了「突破」带来的岔路 → AI 替我选 → AI 替我写 →
  提交后年表上记录了写的那个决定
- **旧契约回归**：创角、导入导出、属性不变量、自定义世界生成、输出截断提示

模拟服务的请求分派改成了**按输出契约识别**（`"index"` / `"action"` / `"entries"`），
而不是按提示词措辞——措辞会变，契约不会。认不出时会在控制台出声，
不再静默回退到「按段落生成处理」。

### 两个「数到别的东西」的断言（写完自查抓到的）

这两条一开始都是通过的，但数的根本不是它们声称在数的东西。**这类断言比没有断言更危险**，
因为它会给出虚假的安全感：

1. `年表：条目按年份分组` 用文本 `/^\d+ 岁$/` 定位年份分组——而条目行里的年龄标签
   文本也是「N 岁」，于是它实际数的是条目数（40 个），不是年份分组数（15 个）。
   改成给年份分组打 `data-year-header`。
2. `崩溃恢复：提示里带上了当时提交的决定` 在全文里找「跟他走」——而刷新后决策卡
   也在页面上，它的选项按钮文案就是「跟他走」。改成把查找范围限定在提示框内部。

同一类问题在 `Timeline` 里也留了注释说明为什么不能靠文本定位。

### 表结构迁移是怎么验的

`storage/migrate.ts` 里的转换逻辑有纯函数单测，但「Dexie 升级时旧表读不读得到」
只有真的开一次库才知道：v3 把 `events` / `pendingTurns` 声明成 `null`（升级后删除），
万一 Dexie 在跑 upgrade 之前就把它们删了，`readLegacyTable` 的兜底会把异常咽下去，
**玩家的全部历史静默消失**，界面上只表现为「年表是空的」。

`src/lib/storage/upgrade.test.ts` 因此用一个 `LegacyDatabase` 类把库建到 v2、
写入旧形状的 `saves` / `events` / `pendingTurns`，再用 `getDb()` 打开触发升级，断言：
字段改名、回合搬进 `segments`、pending 搬家、旧表被删、已结束的存档不留岔路、
以及**升级后的段号接得上、能继续往下写**。七项一次通过。

## 七、已知的后续项

1. **段落数仍未落进方案的 30~60**。要落进去只能重写寿元表或放宽单段跨度上下限，
   两者都属于数值设计决策而非重构，因此没有在这轮里做。当前实测 27~78 段，
   两端各贴着一条上下限（见第四节第 2 条）。

2. **条目粒度的细读体验没有真机验证过**。模拟服务产出的条目是模板化的，
   真实模型会不会把 10 年写成一句话、会不会滥用 `detail`，需要在真实 Key 下观察几局。
   提示词里对「什么算重要」给了清单，也有一条契约断言守着它不被顺手删掉，
   但清单够不够用只能靠看。

3. **密度参数是「对着模拟标定」的，不是从真实模型标定的。** 这一条是**目前最大的
   未知**。`DECISION_GAP_DIVISOR` / `KEYWORD_MIN_GAP` / `TYPICAL_TIER_RATIO`
   三个数都是拿 200 条确定性模拟反推出来的，它们能保证
   **机制不失控**（三种模型形态下都落在 8~15），但保证不了真实模型的提议频率
   落在哪个位置。

   接上真实 Key 跑几局之后，如果介入次数明显偏离 8~15，第一个该动的是
   `pacing.ts` 里的 `DECISION_GAP_DIVISOR`；改完**必须重跑 `npm test -- balance`**——
   它三种形态都会跑，会立刻告诉你有没有踩到另一侧。

4. **`TYPICAL_TIER_RATIO = 0.75` 只在四个内置世界 + 一个生成世界上验过。**
   它是「典型人生能达到多高的阶位」的经验系数。新增题材（尤其是阶位数与寿元
   曲线形状差别大的）之后，值得回头看一眼估算值和实测值差多少——
   `npm test -- balance` 的输出里两列并排，一眼能看出来。
