# 年表式叙事重构方案

> 从「回合制选择题」改为「会自己运转的世界 + 关键时刻介入」
>
> **状态：已实施。** 实施记录、与本文的偏差清单、实测数据见
> `docs/年表叙事重构实施说明.md`。
>
> 本文保留为**当初的设计提案**，正文里的数字不都是最终值。已知四处与实现不一致，
> 读实现前先看实施说明：
> 1. 单段跨度上限（25 → **60 年**）
> 2. 每局段数（30~60 → **实测 27~78**）
> 3. 决策门槛（固定常量 → **按世界规模反推，且按信号强度分层**）
> 4. 条目长度（≤25 字 → **15~40 字**，因为「一句话」的约束被模型读成了「压成主谓宾摘要」）

---

## 一、问题诊断

### 现在的循环

```
读 300~800 字 → 选 1 个 → 读 300~800 字 → 选 1 个 → …
```

一局约 50~100 回合。玩家要读 **约 5 万字**、做 **约 70 次决策**。

### 真正的问题不是「文本长」

单独看，长文本是优点——叙事有质感。问题在于**长文本 + 高频决策**的组合：

| 症状 | 根因 |
| --- | --- |
| 读起来累 | 每次决策前都必须读完一大段，否则不知道在选什么 |
| 决策累赘 | 决策太频繁，边际意义递减。第 40 次选「继续修炼」时，玩家已经没有参与感了 |
| 像在推小说 | 时间是玩家推着走的，世界不会自己运转 |

**关键判断：玩家的注意力应该花在少数几个真正改变命运的节点上，其余时间交给世界自己运转。**

---

## 二、目标形态

> **读年表，而不是读小说；在岔路口才停车。**

三条原则：

1. **时间是主轴，事件是条目** —— 输出以「年」为分组，每年下面是若干一句话条目
2. **默认短，重要才长** —— 绝大多数条目一行；只有突破、死亡、重大转折才展开成完整叙事
3. **只在重要决策处停车** —— 玩家一次介入，换来世界自动运转若干年

### 前后对比

| | 现在 | 重构后 |
| --- | --- | --- |
| 一屏能看多少 | 约 1 回合 = 1~3 年 | 约 20~40 年 |
| 一局决策次数 | 50~100 次 | **8~15 次** |
| 一次模型调用覆盖 | 1~3 年 | 3~25 年 |
| 玩家角色 | 每一步的操作者 | 关键节点的决策者 |

---

## 三、核心循环

```
玩家点「继续」
   ↓
模型推进一段（若干年 / 若干事件），产出条目流
   ↓
程序结算（属性、突破、死亡）并判定是否到达「重要决策点」
   ↓
有决策点 → 停车，插入决策卡，等玩家
无决策点 → 直接追加到年表，玩家可再点「继续」
```

一段覆盖多久由模型决定，程序给上下限（3~25 年，4~12 条条目）。

## 四、数据模型

### 新增：条目与段落

```ts
/** 时间轴上的一个条目。一句话，可扫读。 */
export interface LifeEntry {
  /** 发生时的年龄。程序会校正为单调递增且不超出段尾 */
  age: number;
  /** 条目类型，决定图标与配色 */
  kind: 'cultivation' | 'event' | 'relationship' | 'fortune' | 'setback' | 'milestone';
  /** 一句话，25 字以内 */
  text: string;
  /** 可选。只有重要条目才给，100~200 字的完整叙事 */
  detail?: string;
}

/** 一次自动推进产出的段落。 */
export interface LifeSegment {
  entries: LifeEntry[];
  timeAdvance: number;
  attributeDeltas: Record<string, number>;
  worldStatusUpdate?: string;
  traitOps?: ListOp[];
  inventoryOps?: ListOp[];
  relationshipOps?: RelOp[];
  /** 本段结束时若到达重要决策点，这里给出岔路 */
  decision?: DecisionPoint;
  endingProposal?: { type: 'death' | 'completion'; reason: string };
}

/** 停在玩家面前的一个岔路。 */
export interface DecisionPoint {
  /** 引子，1~3 句话，说清现在发生了什么 */
  prompt: string;
  /** 为什么这是个重要节点。写给玩家看，让他明白这次选择的分量 */
  stakes: string;
  /** 2~4 个选项 */
  options: string[];
  /** 程序侧记录的触发原因，用于调参与展示 */
  cause: DecisionCause;
}

export type DecisionCause =
  | 'proposed'      // 模型提议且通过门槛
  | 'breakthrough'  // 本段发生了阶位突破
  | 'near-end'      // 寿元进入末段
  | 'long-gap';     // 距上次介入太久，强制给一次参与感
```

### 替换：回合事件 → 段落记录

`GameTurnEvent` → `LifeSegmentRecord`：

```ts
export interface LifeSegmentRecord {
  saveId: string;
  segmentId: number;          // 原 turnId
  requestId: string;
  /** 触发本段的决策（第一段没有） */
  playerAction?: string;
  segment: LifeSegment;
  characterBefore: CharacterState;
  resolvedCharacter: CharacterState;
  resolvedWorldStatus: string;
  ending?: Ending;
  validationWarnings: string[];
  modelMeta: ModelMeta;
  schemaVersion: number;
  createdAt: number;
}
```

## 五、重要决策的判定（本方案的核心机制）

延续既有的架构铁律——**模型只提议，程序才结算**。决策点同样如此。

### 调用前：程序告诉模型「这段必须停」

程序先算 `mustStop`：

| 条件 | 说明 |
| --- | --- |
| 距上次决策已自动推进 ≥ 8 段 | 保证参与感不至于消失 |
| 年龄进入当前阶位寿元的末 15% | 终局临近，该给玩家收束的机会 |
| 已连续 3 段没有任何决策 | 兜底 |

命中则在提示词里明确要求「本段结束时**必须**给出一个决策点」。

### 调用后：程序判定模型提议的决策是否采纳

模型给了 `decision`，还要通过以下门槛之一才真的停车：

| 门槛 | 理由 |
| --- | --- |
| 本段属性总变动幅度 ≥ 阈值 | 说明确实是大事，不是日常 |
| 命中「机遇 / 危机」类关键词 | 模型用词可以反映分量 |
| 本段发生了突破 | 突破本身就是岔路 |
| `mustStop` 为真 | 程序侧的强制条件 |

**不通过的决策点直接丢弃**，不打断玩家。

### 密度控制

- 目标：每局 **8~15 次**介入
- 硬约束：**任意 2 段之内最多 1 次决策**，防止模型连续停车
- 这个密度会被写进数值模拟的断言，改提示词后能立刻发现漂移

## 六、阅读负担的处理

三层信息密度：

| 层级 | 内容 | 默认状态 |
| --- | --- | --- |
| 条目 | 一句话，≤25 字 | **展开**（可扫读） |
| 详情 | 100~200 字叙事 | 仅重要条目默认展开，其余折叠 |
| 结局 / 生平 | 完整叙事 | 独立面板 |

**关键规则：只有 `kind === 'milestone'` 或带 `detail` 的条目默认展开。** 其余点击才展开。

这样一屏能看到 20~40 年，而现在的设计一屏只能看到 1 年。

## 七、界面设计

### 主视图：年表

```
┌─ 27 岁 ─────────────────────────────┐
│ · 你闭门不出，修为渐厚          [修行] │
│ · 山下的集市换了新的管事        [世事] │
├─ 28 岁 ─────────────────────────────┤
│ · 你试着冲击筑基，未果          [突破] │
│   ⌄ 展开                              │
├─ 29 岁 ─────────────────────────────┤
│ · 你终于筑基成功                [突破] │
│   三年前那道坎，在某个雪夜忽然通了。    │
│   你走出静室时，天光刺眼。             │
└──────────────────────────────────────┘
```

提供**两种视图切换**：

- **年表**（默认）：以年分组，看得到时间流逝的节奏
- **事件流**：不分年，纯条目列表，更紧凑，适合快速回看

### 决策卡：插在年表末尾

```
┌──────────────────────────────────────┐
│ ⚑ 26 岁 · 这是个岔路                   │
│                                       │
│ 一位自称来自上宗的人找上门，说可以带你  │
│ 走。他的袖口绣着你没见过的纹样。        │
│                                       │
│ 无论怎么选，你都不会再回到从前的日子。  │
│                                       │
│ [ 跟他走 ]  [ 婉拒 ]  [ 追问他的来历 ] │
│                                       │
│ 拿不定主意？ [让 AI 替我选] [替我写]   │
└──────────────────────────────────────┘
```

决策点保留「自由输入」——**这正是自由输入最该出现的地方**。

### 顶部控制

`[ 继续 ]` `[ 连续推进 ×5 ]` `[ 暂停 ]`

「连续推进」让玩家可以一次跑很多段，进一步降低操作负担；遇到决策点自动停。

## 八、提示词重构（工作量最大的部分）

要求模型：

1. 输出**条目流**而不是长散文
2. 自己判断是否到了重要决策点
3. 时间跨度要合理，条目要分布在该段的年份上

### 输出契约

```json
{
  "entries": [
    { "age": 27, "kind": "cultivation", "text": "你闭门不出，修为渐厚" },
    { "age": 28, "kind": "setback", "text": "冲击筑基未果，心气受损" },
    { "age": 29, "kind": "milestone", "text": "筑基成功",
      "detail": "三年前那道坎，在某个雪夜忽然通了。你走出静室时，天光刺眼。" }
  ],
  "timeAdvance": 3,
  "attributeDeltas": { "comprehension": 4, "willpower": -2 },
  "decision": {
    "prompt": "一位自称来自上宗的人找上门，说可以带你走。",
    "stakes": "无论怎么选，你都不会再回到从前的日子。",
    "options": ["跟他走", "婉拒", "追问他的来历"]
  }
}
```

提示词里必须明确**什么算「重要」**（才配给 `detail`、才配当决策点）：

- 配 `detail`：阶位突破、重大际遇、亲密关系的变化、濒死、重要的失去
- 配 `decision`：会改变长期走向的岔路（拜师、迁徙、结仇、托付、放弃）

## 九、结算层的改动

| 改动 | 说明 |
| --- | --- |
| **多次突破** | 一段跨越多年，可能积累多次突破。`resolveSegment` 循环处理直到不再满足条件（上限 5 次） |
| **条目级年龄推进** | 逐条目推进年龄，遇到寿元耗尽就**截断到那一条**并生成结局。条目成为权威时间轴 |
| **时间跨度收紧** | `timeAdvanceHint` 从 1~50 改为 3~25，随阶位上升 |
| **决策点判定** | 新增 `resolveDecision()`，按第五节的门槛决定是否采纳 |

### 需要重新调参

- 一段的时间跨度变了 → 积累曲线与寿元表的相对关系变了
- 一局段数从 50~100 降到 30~60 → 突破次数、回合上限都要重算
- **必须重跑 `npm test -- balance`**，并新增两条断言：每局决策次数落在 8~15、每局段数落在 30~60

## 十、成本影响（顺带的好处）

| | 现在 | 重构后 |
| --- | --- | --- |
| 单次输出 | 600~1000 token（长散文 + JSON） | 300~600 token（条目 + 少量 detail） |
| 覆盖时间 | 1~3 年 | 3~25 年 |
| **单位时间成本** | 基准 | **下降约一个数量级** |

条目化反而更省 token——散文的修辞成本被省下来了，而且省在了最不该花的地方。

## 十一、兼容与迁移

- `schemaVersion: 2`
- **旧存档迁移**：每个旧回合转成一个段落，`entries` 用 narrative 的首句，`detail` 放完整 narrative，界面按「旧版长文」样式渲染
- `pendingTurns` 表语义变为「进行中的段」，改名 `pendingSegments`（Dexie 版本 +1）

保留迁移的理由：导出/导入是已有的玩家资产，直接不兼容会让他们手里的 JSON 变成废纸。

## 十二、分期实施

| 阶段 | 内容 | 可独立验证的产出 |
| --- | --- | --- |
| **1. 数据与提示词** | 定义条目/段落类型、重写提示词、结算层支持条目级推进与多次突破 | 单测：条目解析、年龄截断、多次突破、决策门槛 |
| **2. 界面** | 年表视图（按年分组、条目折叠）、事件流视图、决策卡、顶部控制 | 端到端：推进一段 → 条目出现在年表 → 决策点停车 |
| **3. 决策判定与调参** | 程序侧门槛、密度控制、重跑数值模拟 | 断言：每局决策 8~15 次、段数 30~60 |
| **4. 迁移与收尾** | 旧存档迁移、端到端场景重写 | 旧存档能正常打开并渲染 |

阶段 1 完成前不动界面——数据模型是地基，先立住再往上盖。

## 十三、风险与对策

| 风险 | 对策 |
| --- | --- |
| 模型把条目写成流水账（「你修炼了」×20 条） | 提示词约束条目类型分布；程序侧检查——连续 3 条同 `kind` 视为不合格，回灌重试 |
| 决策点判定不准，模型到处提议 | 程序门槛 + 硬密度上限（2 段内最多 1 次） |
| 模型给出的 age 不单调或不落在段内 | 程序按 `timeAdvance` 校正：单调递增、不超出段尾 |
| 信息密度下降导致「没感觉」 | `detail` 的存在是关键。提示词里明确列出「什么算重要」，保证关键时刻仍有像样的叙事 |
| 一段太长导致细节丢失 | 跨度上限 25 年 + 条目数下限 4 条，逼模型铺开 |

## 十四、需要你拍板的几个点

1. **推进方式** —— 只做「点一下推进一段」，还是加「连续推进」？
   *推荐：两者都做，默认点一下，「连续推进」作为可选项。*

2. **决策密度** —— 目标每局多少次介入？
   *推荐：8~15 次（现在是 50~100 次）。*

3. **长叙事是否保留** —— 完全取消，还是只在重要节点展开？
   *推荐：保留，但只在突破、死亡、重大转折处展开。完全取消会让「重要时刻」失去分量。*

4. **旧存档** —— 迁移保留，还是直接不兼容？
   *推荐：迁移保留。*
